# ☕ K사 커피 주문 시스템

포인트를 충전하여 커피를 주문하고 결제할 수 있는 백엔드 서버입니다.

단순한 CRUD 구현을 넘어 **동시성 제어, 트랜잭션, 중복 요청 방지, Transactional Outbox, 멀티 인스턴스 환경에서의 데이터 정합성**을 고려하여 설계합니다.

## 1. 프로젝트 개요

### 프로젝트 목적

커피 메뉴 조회부터 포인트 충전, 포인트를 이용한 주문 및 결제, 인기 메뉴 조회, 외부 데이터 수집 플랫폼으로의 주문 정보 전송까지 제공하는 REST API 서버를 구현합니다.

특히 여러 서버 인스턴스에서 동시에 요청이 들어오는 상황에서도 포인트 잔액과 주문 데이터의 정합성을 보장하는 것을 주요 목표로 합니다.

### 주요 요구사항

* 커피 메뉴 목록 조회
* 사용자 포인트 충전
* 포인트를 이용한 커피 주문 및 결제
* 주문 완료 후 외부 데이터 수집 플랫폼으로 주문 정보 전송
* 최근 7일 인기 메뉴 TOP 3 조회
* 동시 요청 상황에서 포인트 잔액 정합성 보장
* 중복 주문 요청 방지
* 멀티 인스턴스 환경 고려

## 2. 주요 기능

### 2.1 메뉴 조회

등록된 커피 메뉴의 메뉴 ID, 메뉴명, 가격을 조회합니다.

### 2.2 포인트 충전

1원 = 1포인트를 기준으로 포인트를 충전합니다.

* 최초 충전 시 포인트 계정 생성
* 기존 계정은 잔액 증가
* 포인트 잔액 변경과 충전 이력을 하나의 트랜잭션으로 처리
* 동시 충전 요청에 대한 데이터 정합성 보장

### 2.3 커피 주문 및 결제

포인트를 이용하여 커피를 주문하고 결제합니다.

주요 처리 순서는 다음과 같습니다.

> 메뉴 조회 → 포인트 계정 잠금 → 잔액 확인 → 주문 생성 → 포인트 차감 → 결제 이력 저장 → Outbox 이벤트 저장 → COMMIT

처리 중 오류가 발생하면 관련 변경사항을 모두 롤백합니다.

### 2.4 인기 메뉴 조회

최근 7일 동안 결제 완료된 주문을 기준으로 인기 메뉴를 조회합니다.

* 결제 완료(PAID) 주문만 집계
* 주문 횟수 기준 내림차순
* 주문 횟수가 같으면 메뉴 ID 오름차순
* 상위 3개 메뉴 조회

### 2.5 외부 데이터 수집 플랫폼 전송

주문 완료 후 다음 정보를 외부 데이터 수집 플랫폼으로 전달합니다.

* eventId
* userId
* menuId
* paidAmount

외부 API 호출을 주문 트랜잭션 내부에서 직접 수행하지 않고 **Transactional Outbox 패턴**을 사용하여 처리합니다.

주문 트랜잭션에서는 Outbox 이벤트를 저장하고, 트랜잭션이 성공적으로 커밋된 이후 별도의 작업자가 외부 API로 전송합니다.

전송 실패 시 재시도할 수 있도록 설계하며, 멀티 인스턴스 환경에서 동일한 이벤트가 중복 처리되지 않도록 이벤트 ID를 사용합니다.

## 5. 데이터베이스 설계

주요 테이블은 다음과 같습니다.

* `POINT_ACCOUNT`

  * 사용자별 포인트 계정 및 잔액 관리
* `COFFEE_MENU`

  * 커피 메뉴 및 가격 관리
* `COFFEE_ORDER`

  * 주문 및 결제 정보 관리
* `POINT_HISTORY`

  * 포인트 충전 및 결제 이력 관리
* `OUTBOX_EVENT`

  * 외부 데이터 수집 플랫폼 전송을 위한 이벤트 관리

### 테이블 관계

```text
POINT_ACCOUNT 1:N COFFEE_ORDER N:1 COFFEE_MENU

POINT_ACCOUNT 1:N POINT_HISTORY

COFFEE_ORDER 1:0..1 POINT_HISTORY

OUTBOX_EVENT
└── 외부 시스템 전송을 위한 독립적인 이벤트 저장
```

자세한 ERD는 [docs/erd.md](docs/erd.md)를 참고합니다.

## 7. 핵심 설계

### 7.1 포인트 동시성 제어

여러 주문 요청이 동시에 들어오는 경우 포인트 잔액에 대한 동시성 문제가 발생할 수 있습니다.

예를 들어 한 사용자의 잔액이 10,000포인트이고 동시에 7,000포인트의 주문이 두 번 요청되었다고 가정합니다.

두 요청이 동시에 잔액을 확인하면 모두 결제가 가능하다고 판단할 수 있습니다.

이를 방지하기 위해 `POINT_ACCOUNT`의 해당 행에 대해 **비관적 락(Pessimistic Lock)**&#xC744; 사용합니다.

첫 번째 요청이 계정 행을 잠그면 두 번째 요청은 대기하고, 첫 번째 요청이 커밋된 이후 변경된 잔액을 다시 확인합니다.

따라서 최종적으로 하나의 주문만 성공하고 다른 주문은 잔액 부족으로 실패하도록 처리합니다.

### 7.2 트랜잭션

주문 처리 과정에서 다음 작업을 하나의 트랜잭션으로 묶습니다.

* 주문 생성
* 포인트 차감
* 포인트 결제 이력 저장
* Outbox 이벤트 저장

모든 작업이 성공하면 COMMIT하고, 중간에 하나라도 실패하면 전체 작업을 ROLLBACK합니다.

이를 통해 주문 데이터와 포인트 잔액 사이의 정합성을 유지합니다.

### 7.3 중복 요청 방지

네트워크 재전송이나 사용자의 중복 요청으로 동일한 주문이 여러 번 생성되는 것을 방지하기 위해 `X-Idempotency-Key`를 사용합니다.

동일한 사용자와 동일한 Idempotency Key로 다시 요청하면 기존 주문을 반환합니다.

반면 동일한 Idempotency Key를 사용하면서 다른 주문을 요청하면 충돌로 처리합니다.

DB의 Unique Constraint를 함께 사용하여 애플리케이션 레벨의 중복 방지만으로 발생할 수 있는 Race Condition을 방어합니다.

### 7.4 Transactional Outbox

주문 데이터와 외부 시스템 전송 이벤트의 정합성을 보장하기 위해 Transactional Outbox 패턴을 적용합니다.

주문 트랜잭션에서 외부 API를 직접 호출하지 않고 `OUTBOX_EVENT`에 이벤트를 저장합니다.

```text
주문 요청
   ↓
주문 생성
   ↓
포인트 차감
   ↓
결제 이력 저장
   ↓
Outbox 이벤트 저장
   ↓
COMMIT
   ↓
Outbox Worker
   ↓
외부 데이터 수집 플랫폼 전송
```

외부 API 호출은 주문 트랜잭션과 분리하여 처리합니다.

전송에 실패하면 재시도하고, 여러 서버 인스턴스가 동시에 동일한 이벤트를 처리하지 않도록 이벤트 선점 및 재시도 정책을 적용합니다.

단, 외부 시스템까지 완전한 exactly-once 전달을 보장하는 것은 아니므로 `eventId`를 이용한 중복 처리 방지를 함께 고려합니다.

### 7.5 멀티 인스턴스 환경

여러 서버 인스턴스가 동시에 실행되는 환경을 고려합니다.

데이터의 기준은 애플리케이션 서버가 아닌 DB에 두고, 포인트 잔액 변경에는 DB Row Lock을 사용합니다.

Outbox Worker 역시 여러 서버에서 동시에 실행될 수 있으므로 이벤트를 처리하기 전에 DB에서 작업 대상을 선점하도록 설계합니다.

## 8. 인기 메뉴 조회 전략

최근 7일 동안 결제 완료된 주문을 기준으로 메뉴별 주문 횟수를 집계합니다.

```sql
SELECT
    menu_id,
    COUNT(*) AS order_count
FROM coffee_order
WHERE status = 'PAID'
  AND paid_at >= :sevenDaysAgo
  AND paid_at < :now
GROUP BY menu_id
ORDER BY order_count DESC, menu_id ASC
LIMIT 3;
```

조회 성능을 고려하여 다음과 같은 인덱스를 후보로 검토합니다.

```text
(status, paid_at, menu_id)
```

실제 구현 후 실행 계획을 확인하여 인덱스 적용 효과를 검증합니다.

* 잘못된 충전 금액

* 기존 계정 충전
* 동시에 여러 충전 요청

### 주문

* 정상 주문
* 존재하지 않는 메뉴
* 포인트 계정이 없는 경우
* 포인트 부족
* 동시에 여러 주문 요청
* 동일한 Idempotency Key로 중복 요청
* 동일한 Key로 다른 주문 요청
* 주문 실패 시 포인트 및 주문 데이터 롤백

### 인기 메뉴

* 최근 7일 주문 집계
* 7일 범위 경계값
* PAID 주문만 집계
* 주문 횟수가 같은 경우 메뉴 ID 기준 정렬
* TOP 3 제한

### Outbox

* 주문과 Outbox 이벤트가 동일 트랜잭션으로 저장되는지 확인
* 주문 실패 시 Outbox도 저장되지 않는지 확인
* 외부 전송 성공
* 전송 실패 및 재시도
* Worker 장애 후 이벤트 재처리
* 멀티 인스턴스 환경에서 동일 이벤트 중복 처리 방지
